# Iris Garden

A flower shop: storefront, customer accounts and admin in one Next.js app. Payload
runs the CMS, the database and the admin panel; the storefront reads it through
Payload's Local API, so there are no internal HTTP calls between the two halves.

- **Framework** — Next.js 16 (App Router, React 19, Turbopack)
- **CMS + data** — Payload 3 on Postgres (Neon)
- **Uploads** — Neon Object Storage (S3 API); local disk when no S3 keys are set
- **Hosting** — Vercel
- **Styling** — Tailwind CSS v4, no component library

## Getting started

You need a Postgres database. A Neon branch is the easiest; a local Postgres works too.

```bash
npm install
cp .env.example .env     # then fill in PAYLOAD_SECRET and DATABASE_URI
npm run seed             # photos, 15 products, 4 categories, an admin user
npm run dev
```

- Storefront — http://localhost:3000
- Admin — http://localhost:3000/admin

The seed creates an admin from `SEED_EMAIL` / `SEED_PASSWORD`. Against `localhost` it
falls back to `admin@irisgarden.com` / `changeme123`; against any other database it
refuses to run unless `SEED_PASSWORD` is set.

Everything optional in `.env` degrades quietly: with no Google keys the Google
buttons do not render, with no SMTP host Payload logs emails to the console, and with
no `S3_ACCESS_KEY_ID` uploads go to `public/media`.

## Scripts

| Command | What it does |

| `npm run dev` | Storefront and admin on :3000 |
| `npm run build` / `npm start` | Production build and server |
| `npm run vercel-build` | What Vercel runs: `payload migrate`, an optional seed, then `next build` |

| `npm run generate:importmap` | Regenerate the admin import map after adding a custom admin component or a plugin that ships one |
| `npx payload migrate:create <name>` | Write a migration for the schema change you just made |
| `npx payload migrate` | Apply pending migrations |
| `npm run lint` | ESLint |

## Changing the schema

Whenever you edit a collection or global:

1. `npm run generate:types` — the storefront is typed against `payload-types.ts`.
2. `npx payload migrate:create <name>` and commit the new file in `migrations/`.

Generate migrations with the S3 variables set (dummy values are fine): the storage
plugin adds an `_objectKey` column to `media` only when it is enabled, so a migration
made without them leaves production without that column and the build fails.

Production never relies on Payload's dev-time schema push. Vercel runs
`payload migrate` before every build, so the migration is applied as part of the
deploy. Upgrading Payload can also need a migration (3.89 -> 3.91 added
`reset_password_requested_at` to the auth collections), so run `migrate:create`
after a Payload upgrade too and check that it produces nothing unexpected.

Preview deployments use the same `DATABASE_URI` as production unless you scope a
different one to Preview, so a preview build also migrates that database. Keep
migrations additive, or give Preview its own Neon branch.

## Layout

```
app/
  (frontend)/        storefront, account pages, Google OAuth routes
  (payload)/         admin panel and REST API, generated by Payload

components/          storefront UI
lib/                 cart store, auth, order builder, money, rate limiting and query helpers
migrations/          Payload database migrations (applied by `payload migrate`)
scripts/             seed and checks
neon.ts              Neon CLI project config (branch policy, the storage bucket)
payload.config.ts    collections, database, email, storage and admin config
```

## Deploying

Vercel builds from `main` with `npm run vercel-build`. Set these in the Vercel
project (Production and Preview); `.env.example` documents every one:

| Variable | Notes |
| --- | --- |
| `PAYLOAD_SECRET` | Long random string; changing it signs everyone out |
| `DATABASE_URI` | Neon **pooled** (`-pooler`) connection string; use `sslmode=verify-full` |
| `NEXT_PUBLIC_SITE_URL` | The public URL; used for the sitemap, share tags and Google's redirect |
| `S3_BUCKET`, `S3_REGION`, `S3_ENDPOINT`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | Neon Object Storage; the bucket is private and Payload streams files through `/api/media/file/*` |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | Optional |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `EMAIL_FROM` | Needed for order confirmation emails |
| `SEED_EMAIL`, `SEED_PASSWORD` | Used only when seeding |
| `SEED_ON_BUILD` | Set to any value for **one** build to seed the database, then remove it. The seed wipes products, categories and media. Keep it off Production and Preview |

## Data model

**Products** carry a price in dollars, images, a category, occasion tags, an
`inStock` flag and optional sizes. A size is a label plus a price delta, so
"Large +$28" is stored as `28`, not as a second product. Products are versioned
with drafts, so a new bouquet stays invisible to the storefront until published.

**Categories** are flat and ordered by an `order` field. Occasions are not a
collection — they are a fixed list in `lib/occasions.ts` shared by the Payload
field options and the storefront filter chips.

**Orders** snapshot what was bought: title, size and unit price at the moment of
purchase. Editing a product later never rewrites an old order. An order links to
a `Customer` when one was signed in, and stays standalone for guest checkout.

**Customers** is a separate auth collection from **Users** (the studio staff).
Customers can never reach the admin panel, and access control scopes every read
and write to their own record and their own orders.

**Settings** holds the standard delivery fee, per-zone fees, the free-delivery
threshold, the same-day cutoff hour, contact details and the home page hero.

## Money

Product prices are stored in dollars because that is what admins type. Everything
from the cart onwards is integer cents, so totals cannot drift. The two
conversions live in `lib/money.ts` and nowhere else.

The cart holds product ids, sizes, quantities and the prices it last displayed.
When an order is placed, `lib/order.ts` re-reads every price, size delta and
delivery fee from the database. The displayed prices are compared but never
used: if any of them has moved, the order is refused, the cart adopts the real
prices and the customer is asked to confirm the new total. Nobody is ever charged
a number they have not seen.

`npm run check` asserts all of this, including forged sizes, out-of-range
quantities, per-zone fees and the delivery cutoff.

## Accounts

Customers can register with an email and password, or through Google. Both paths
mint the same Payload session cookie via Payload's own exported helpers
(`getFieldsToSign`, `jwtSign`, `generatePayloadCookie`) — there is no hand-rolled
JWT anywhere.

To switch Google sign-in on:

1. In Google Cloud Console create an OAuth 2.0 Client ID of type *Web application*.
2. Add `<NEXT_PUBLIC_SITE_URL>/auth/google/callback` as an authorised redirect URI.
3. Put the client ID and secret in `.env` and restart.

Accounts are matched by email address, and only when Google reports the address
as verified. Signing in with Google for the first time on an address that already
has a password account links the two rather than creating a duplicate.

Guest checkout still works with no account at all. Guests can reach a past order
at `/order/lookup` with the order number plus the email they ordered with.

## Caching

Product pages are prerendered with `generateStaticParams`. Payload `afterChange`
and `afterDelete` hooks call `revalidatePath`, so an admin edit shows up
immediately; the one-hour `revalidate` on those pages is only a backstop.

The root layout deliberately does **not** read the session — doing so would opt
every page into dynamic rendering. The header always links to `/account`, which
redirects to the login page when there is no session.

## Before this goes live

- **Domain** — Vercel's deployment protection puts `*.vercel.app` URLs behind a Vercel
  login. Attach a custom domain (or switch protection off for production), then update
  `NEXT_PUBLIC_SITE_URL`.
- **Google sign-in** — add `<NEXT_PUBLIC_SITE_URL>/auth/google/callback` as an
  authorised redirect URI on the OAuth client.
- **Email** — set the `SMTP_*` variables. Without them nobody receives their order
  number.
- **Photos and copy** — the seed pulls demo images from Unsplash and uses placeholder
  contact details. Replace the photos, products and Settings (phone, address,
  Instagram) in the admin.
- **Seed credentials** — the seed refuses a non-local database without
  `SEED_PASSWORD`, and does not print a real password. Change the admin password
  after first login.
- **Backups** — Neon's free plan keeps only a few hours of history. Protect the
  production branch and plan backups before taking real orders.
- **Payments** — orders are cash on delivery and are created with status
  `pending`. A gateway would hook into `placeOrder` in
  `app/(frontend)/checkout/actions.ts`.
- **Rate limiting** — `lib/rateLimit.ts` counts in Postgres (the `rate-limits`
  collection), so the budget is shared by every instance. It uses fixed windows, so a
  burst straddling a window boundary can get up to twice the limit.

## Not built

Payments, stock counts (a bouquet is either available or not), discount codes,
reviews, analytics and error tracking, and multi-language content. Payload's
localization can be switched on later without rewriting the pages.
