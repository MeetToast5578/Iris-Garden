# Iris Garden

A flower shop: storefront, customer accounts and admin in one Next.js app. Payload
runs the CMS, the database and the admin panel; the storefront reads it through
Payload's Local API, so there are no internal HTTP calls between the two halves.

- **Framework** — Next.js 16 (App Router, React 19, Turbopack)
- **CMS + data** — Payload 3 on SQLite
- **Styling** — Tailwind CSS v4, no component library

## Getting started

```bash
npm install
cp .env.example .env     # then fill in PAYLOAD_SECRET
npm run seed             # photos, 15 products, 4 categories, an admin user
npm run dev
```

- Storefront — http://localhost:3000
- Admin — http://localhost:3000/admin (`admin@irisgarden.com` / `changeme123`)

Everything optional in `.env` degrades quietly: with no Google keys the Google
buttons do not render, and with no SMTP host Payload logs emails to the console.

## Scripts

| Command | What it does |
| --- | --- |
| `npm run dev` | Storefront and admin on :3000 |
| `npm run build` / `npm start` | Production build and server |
| `npm run seed` | Rebuild the demo catalogue (deletes products, categories and media — leaves orders, customers and messages alone) |
| `npm run check` | Assertions over cart rules, shop filters and checkout pricing |
| `npm run generate:types` | Regenerate `payload-types.ts` after editing a collection |
| `npm run generate:importmap` | Regenerate the admin import map after adding a custom admin component |
| `npm run lint` | ESLint |

Run `generate:types` after any change to a collection or global — the storefront
is typed against that file.

## Layout

```
app/
  (frontend)/        storefront, account pages, Google OAuth routes
  (payload)/         admin panel and REST API, generated by Payload
collections/         Products, Categories, Media, Orders, Customers, ContactMessages, Users
globals/Settings.ts  delivery fees and zones, cutoff hour, contact details, hero
components/          storefront UI
lib/                 cart store, auth, order builder, money and query helpers
scripts/             seed and checks
payload.config.ts    collections, database, email and admin config
```

## Data model

**Products** carry a price in dollars, images, a category, occasion tags, an
`inStock` flag and optional sizes. A size is a label plus a price delta, so
"Large +$28" is stored as `28`, not as a second product. Products are versioned
with drafts, so a new bouquet stays invisible to the storefront until published.

**Categories** are flat and ordered by an `order` field. Occasions are not a
collection — they are a fixed list in `lib/occasions.ts` shared by the Payload
field options and the storefront filter chips.

**Orders** snapshot what was bought: title, size and unit price at the moment of
purchase. Editing a product later never rewrites an old order. An order links to
a `Customer` when one was signed in, and stays standalone for guest checkout.

**Customers** is a separate auth collection from **Users** (the studio staff).
Customers can never reach the admin panel, and access control scopes every read
and write to their own record and their own orders.

**Settings** holds the standard delivery fee, per-zone fees, the free-delivery
threshold, the same-day cutoff hour, contact details and the home page hero.

## Money

Product prices are stored in dollars because that is what admins type. Everything
from the cart onwards is integer cents, so totals cannot drift. The two
conversions live in `lib/money.ts` and nowhere else.

The cart holds product ids, sizes, quantities and the prices it last displayed.
When an order is placed, `lib/order.ts` re-reads every price, size delta and
delivery fee from the database. The displayed prices are compared but never
used: if any of them has moved, the order is refused, the cart adopts the real
prices and the customer is asked to confirm the new total. Nobody is ever charged
a number they have not seen.

`npm run check` asserts all of this, including forged sizes, out-of-range
quantities, per-zone fees and the delivery cutoff.

## Accounts

Customers can register with an email and password, or through Google. Both paths
mint the same Payload session cookie via Payload's own exported helpers
(`getFieldsToSign`, `jwtSign`, `generatePayloadCookie`) — there is no hand-rolled
JWT anywhere.

To switch Google sign-in on:

1. In Google Cloud Console create an OAuth 2.0 Client ID of type *Web application*.
2. Add `<NEXT_PUBLIC_SITE_URL>/auth/google/callback` as an authorised redirect URI.
3. Put the client ID and secret in `.env` and restart.

Accounts are matched by email address, and only when Google reports the address
as verified. Signing in with Google for the first time on an address that already
has a password account links the two rather than creating a duplicate.

Guest checkout still works with no account at all. Guests can reach a past order
at `/order/lookup` with the order number plus the email they ordered with.

## Caching

Product pages are prerendered with `generateStaticParams`. Payload `afterChange`
and `afterDelete` hooks call `revalidatePath`, so an admin edit shows up
immediately; the one-hour `revalidate` on those pages is only a backstop.

The root layout deliberately does **not** read the session — doing so would opt
every page into dynamic rendering. The header always links to `/account`, which
redirects to the login page when there is no session.

## Before this goes live

- **Photos** — the seed pulls demo images from Unsplash. Replace them with your
  own in the admin before launching.
- **Seed credentials** — `changeme123` is in this repo. Always set `SEED_EMAIL`
  and `SEED_PASSWORD` when seeding anything that is not localhost.
- **Database** — SQLite is a file on disk. On a platform with an ephemeral
  filesystem, swap `sqliteAdapter` in `payload.config.ts` for
  `@payloadcms/db-postgres`. Collections do not change.
- **Uploads** — media is written to `public/media`, which has the same
  constraint. Serverless hosts need a storage adapter (`@payloadcms/storage-s3`
  or similar).
- **Payments** — orders are cash on delivery and are created with status
  `pending`. A gateway would hook into `placeOrder` in
  `app/(frontend)/checkout/actions.ts`.
- **Rate limiting** — `lib/rateLimit.ts` counts in process, so the budget is per
  instance. Behind more than one server, move it to Redis or the platform's edge
  limiter.
- **Schema changes on real data** — SQLite's dev push rebuilds tables and cannot
  always migrate in place (turning on drafts is one such case). Use
  `payload migrate:create` against a database you care about rather than relying
  on push.

## Not built

Payments, stock counts (a bouquet is either available or not), discount codes,
reviews, analytics and error tracking, and multi-language content. Payload's
localization can be switched on later without rewriting the pages.
